## N 軸とは何か

★**ブラウザが実際に何を叩いているかを、Excel VBA だけで見る。**★
F12 の Network タブに相当するものを、外部ライブラリゼロで作る。

### なぜコンセプトに合うのか

コンセプト① (Web ページを自動制御することに優れた使いやすさ) の ★前段★ は、
必ず「何を叩けばよいかを調べる」である。そこが一番面倒だという実務からの声が
発端になった (2026-08-25 たーぼーさん):

> 基幹システムを操作して CSV を吐かせ、それを PowerShell で自動化した。
> HTTP で POST したりレスポンスを読むために ★F12 の Network タブのログを調査する
> 部分が非常に面倒★ だった。必要な部分だけ抽出できる調査ツールが作れないか。

★出口まで含めると、F12 に無い価値になる★ ―― キャプチャした要求を
**PowerShell の `Invoke-WebRequest` コードとして吐く**。「ブラウザで 1 回手で操作 →
その通信を PowerShell コードで受け取る → タスクスケジューラに載せる」という
実務の流れが、そのまま道具になる (`Copy as cURL` はあっても PowerShell 版は無い)。

#### ★記録だけしてすぐ返す (論点5) の徹底★

受け口 (`View_OnWebResourceRequested`) の中では

- `Wv2Log` も `Debug.Print` も撃たない ―― ★他の `Case` にある 4 行の
  `Debug.Print` を、この種別だけ意図的に外した★
- `dcf` / `GetStringProperty` に渡す `funcName` も空にして、失敗しても
  イミディエイトに何も出さない (失敗はリングに `(err)` として書き残す)
- ★エラーを再送出しない★ ―― 他の受け口は `Err.Raise` するが、通信の最中に
  エラーダイアログが出ると操作が続けられない。握り潰した事実は
  `NetLogDrain` の出力に必ず現れる

`get_Request` は AddRef 済みで返るので必ず `ComRelease` する。1 ページで数百回
通る経路なので、ここを漏らすと目に見えて漏れる。

#### 経過 ms の時刻源に `GetTickCount` を使った

★`Timer` は使えない★ ―― `Timer` は Single の「午前 0 時からの秒」なので、
午後の値 (5 万秒台) では Single の有効桁が足りず ms の分解能が消える。
さらに日付を跨ぐと巻き戻る。`GetTickCount` は起動からの ms で単調増加。
戻り値は Long なので約 49.7 日で一周するが、差を Double に上げて計算し、
負になったら 2^32 を足して戻している (`NetElapsedMs`)。

  ランタイムが内部の資材ハンドラで直接返しているため。★配信自体は問題なくできる。
  乗らないのはイベントだけ★ なので、検証ページは仮想ホストのままでよく、
  **的だけを外に出せばよい**。

- **仕様事実70** ★JS の `fetch()` の要求は `FETCH`(8) ではなく
  `XML_HTTP_REQUEST`(7) として届く★。実機で fetch 10 本を撃って 10 本とも XHR。
  種別で絞り込むときに決めつけないこと。既定のフィルタは `FETCH`(8) も
  張ったままにしてある (害はなく、将来変わっても拾える)。

- **仕様事実71** ★`http://127.0.0.1:<port>` は https のページから呼んでも
  混在コンテンツで止まらない★ (仕様上「潜在的に信頼できるオリジン」)。
  ただし ★Chromium が塞いでいるポート (1/7/9/11/13/…/10080 など) は避ける★。
  この 2 つを踏まえれば、★到達不能なローカルアドレスは「外部依存ゼロで
  ネットワーク要求を発生させる的」として使える★ (接続は失敗するが要求は飛ぶ)。
