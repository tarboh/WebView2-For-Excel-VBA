## K-1 段階 — デバッグログのファイル出力 (`Wv2Log`)

### 位置づけ

D-2 の実機検証で、**イミディエイトウィンドウの保持行数が足りず前半のログが流れて
確認できない**事態が起きた。ハンドルの連番から健全性は確定できたが、
★流れたことに気づけない★のが本質的な危険だった。

D 軸は 1 テストで数十往復するので今後必ず再発する。**以降のすべての検証の土台。**
たーぼーさん自身が「テキストファイルに出力する仕組みとか作った方が良くないか？」と
提案し、D-2 完了時点で「次はこれ」と合意していた宿題。

E-3 で `import.ps1 -AllowNew` が動くようになったため、`Wv2Log.bas` を
**VBE で手作りせずに投入できる**状態になってから着手した。

### `Wv2Log` の API

```vba
Wv2Log.LogE "..."      ' ERROR (書いた直後に強制フラッシュ)
Wv2Log.LogW "..."      ' WARN  (同上)
Wv2Log.LogI "..."      ' INFO
Wv2Log.LogD "..."      ' DEBUG

?Wv2Log.LogPath        ' 今のログファイルのフルパス
Wv2Log.LogLevel = LOG_WARN   ' しきい値
Wv2Log.LogEcho = False       ' イミディエイトへの併記を止める
Wv2Log.LogStart        ' 新しいログに切り替える (検証の仕切り直し)
Wv2Log.LogStop / LogFlush
```

出力はこうなる。

```
=== Wv2Log 開始 2026-08-20 08:36:20 ===
=== path = C:\Users\gugug\AppData\Roaming\Wv2Browser\logs\wv2_20260820_083620.log ===
=== 行頭の 6 桁は連番。欠番があればログが落ちている ===
000001 2026-08-20 08:36:20.033 [ERR ] K-1: ERROR の行
000002 2026-08-20 08:36:20.033 [WARN] K-1: WARN の行
```

### ★行に連番を振った★ (論点に無かった追加)

**K-1 の動機は「流れたことに気づけない」ことなので、気づける仕掛けを入れないと
問題を半分しか解いていない。** 行頭の 6 桁を見て欠番があれば落ちている。

検証 Sub もこれを見ており、「連番に欠番が無い」を合否条件に入れてある。

### 実装前に済ませた検査

- **識別子の衝突検査を新設** (`tools/check_idents.py`)。既存 748 種と小文字化して照合。
  `Wv2Log` で使う 50 個の識別子すべてが衝突なしであることを確認してから書き始めた。
- **UTF-8 エンコーダを Python で先に再現**し、**U+0020〜U+FFFF 全部** +
  補助面を間引いた総当たりで Python の `encode('utf-8')` と一致することを確認。
- **整形・構文検査を新設** (`tools/check_vba.py`)。定型検査 1 番の常設化。

### ★踏んだ罠: 設計原則29 (危うくサロゲート判定が死ぬところだった)★

サロゲートペアの判定に書いた `&HD800` / `&HDBFF` / `&HDC00` / `&HDFFF` は、
いずれも `&H7FFF` を超える。**`&` サフィックスが無いと負の Integer として評価され、**

```vba
If logCode >= &HD800 And logCode <= &HDBFF Then
```

**この条件が永久に成立しない。** 4 バイト文字が黙って壊れる、目視では気づけない不具合。
新設した `check_vba.py` が検出し、コードを渡す前に潰せた。

★さらに import 後に裏付けが取れた★ VBE は `&H10000&` / `&H40000&` の**冗長な `&` を
落とした**のに、`&HD800&` / `&HDC00&` は**残した**。
**VBE 自身が「危険域は 0x8000〜0xFFFF だけ」と判断している。** 検査器の閾値と一致した。

### 確立した設計原則 (99〜100)

## ★ 設計原則 99 — 「無いことの確認」は、対象を読めたことを確かめてから行う ★

空文字に対する検索は何でも「無い」と答える。読み取りに失敗した状態で
「〜が無いこと」を確認すると、**壊れているのに合格する。**

K-1 の 1 回目で実際にこれを踏んだ。ログを読み戻せていないのに
「しきい値で切った INFO が無い」が合格していた。

対策は単純で、**読めたことを先に確かめ、読めなければ以降の照合を打ち切る。**
打ち切ったことを出力に明記すれば、合格数の水増しにもならない。

## ★ 設計原則 100 — 検証が落ちたら、まず「測り方」が対象を測れているかを疑う ★

K-1 は 2 回続けて落ちたが、**2 回とも原因は検証 Sub の側**で、
`Wv2Log` は最初から正しく動いていた。

- 1 回目: 読み取りツール (ADODB) がファイルを開けなかっただけ
- 2 回目: そのツールでは**原理的に測れない性質**を測ろうとしていた

道具の制約を対象の欠陥と取り違えると、正しいものを壊しに行ってしまう。
**落ちた項目の周辺を、対象とは別の経路で直接確かめる**のが最短の切り分けになる
(K-1 では、ログファイルを Python で直接読んで「中身は完璧」と即断できた)。

### 確立した仕様事実 (44〜46)

## ★ 仕様事実 44 — `ADODB.Stream.LoadFromFile` は他のハンドルが開いているファイルを開けない ★

★共有モードに関わらず開けない★ (実測)。書き手が `Shared` (ロックなし) で
開いていても `ファイルを開けませんでした (3002)` になる。

一方、**共有モードを明示する読み手なら開ける。**
VBA なら `Open path For Binary Access Read Shared As #n`。
実行中のログを読みたいときは ADODB を使ってはいけない。

## ★ 仕様事実 45 — `Debug.Print` は CP932 で表示するが、String 自体は無傷 ★

CP932 に無い文字を `Debug.Print` すると `?` になる。
**しかしそれは表示だけの話で、VBA の String は UTF-16 のまま無傷。**
UTF-8 でファイルに書けば正しく残る。

K-1 の実測では、イミディエイトに `サロゲートペア [??]` と出た同じ行が、
ログファイルでは `サロゲートペア [😀]` になっていた。

★イミディエイトの `?` を見て「データが壊れた」と早合点しないこと。★
仕様事実35 (ソースが CP932 に縛られる) とは別の話である。

## ★ 仕様事実 46 — VBE は `&H` リテラルの冗長な `&` サフィックスを落とす ★

`&H10000&` / `&H40000&` は import 後に `&H10000` / `&H40000` になる
(0x10000 以上は最初から Long なので `&` が要らない)。

一方 **`&HD800&` / `&HDC00&` の `&` は残る。**
0x8000〜0xFFFF は `&` が無いと Integer に化けるため、VBE も意味があると判断している。

★設計原則29 の危険域が「0x8000〜0xFFFF」であることの、VBE 自身による裏付け。★
import 後に `&` が消えていても破損ではない。

## K-2 段階 — 設定タブが検索で潰れるバグの修正

### 位置づけ

D-2 の回帰確認で見つかり、宿題に積んであった既存バグ。第9.19 (`IsSettings` 導入) と
第9.24 (NavBar の Host 一元化) の隙間にあったもので、D-2 とは無関係。
9.xx は凍結済みなので、借金返済として K 軸で扱った。

**症状**: 設定タブがアクティブな状態でアドレスバーに検索語を入れると、設定タブ自身が
検索結果へ遷移して設定画面が消える。さらに歯車を押しても「既に設定タブがある」と
判定されて新しい設定タブが開かない。

### 真因と、対症療法が効かない理由

`IsSettings` は生成時に立てたきり、**遷移しても `False` に戻らなかった**。
フラグが実態を反映していないので、`OpenSettingsTab` の重複判定が
「元・設定タブ」を掴んでいた。

★**アドレスバーだけの問題ではない**★
フラグがズレる原因は「遷移したこと」なので、**リンククリック・戻る・進む・リロード・
JS 由来の遷移**でも同じことが起きる。`NavigateActive` を塞ぐ対症療法では直らない。

この見立てが、後の案の選択を決めた。

### 論点と決定

当初 6 件で合意したが、**たーぼーさんの指摘で論点4 を撤回し、論点7 を追加した**。

|---|---|---|
| 1 | 段階番号 | **K-2** (借金返済) |
| 2' | 判定の方法 | **A-2: `EvalSync` で各タブに直接聞く** (下記) |
| 3 | 判定式 | 設定 HTML に `window.__wv2Settings = true` を埋め、`(window.__wv2Settings===true)?'yes':'no'` を尋ねる |
| 4 | ~~戻るで復帰したらフラグを復活させるか~~ | **★撤回★** 下記 |
| 5 | ログ | 判定と同期の結果を `Wv2Log` に出す (K-1 の初仕事) |
| 6 | 検証 | `Test_K2_Help` に手順を出す。設定タブは実起動が要るので自動化しきれない |
| 7 | **設定ビューが重なったときの食い違い** | **B-1: 設定が変わったら表示中の全タブへ現在値を押し込む** (新規) |

### ★指摘による設計の組み直し★

当初は論点4 で「戻るで設定画面へ復帰してもフラグは復活させない。設定タブが 2 枚に
なりうるが実害は小さい」と書いた。これに対してたーぼーさんから

> 複数の設定タブの片方で設定を変更したとき、もう片方のタブの設定との矛盾が
> 発生するのが気になる

という指摘を受けた。**この指摘は正しく、私の評価が誤っていた。**

設定画面の JS は**読み込み時に `S.GetEngine()` で現在値を取り `current` に保持する**
実装なので、後から別のタブで変更しても、先に開いた側は古い値を表示し続ける。
「見た目の重複」ではなく**状態の食い違い**だった。

さらに調べて分かったのは、**問題が 2 つに分かれている**こと:

- **(a) 歯車が「元・設定タブ」を掴む** … 判定の精度の問題
- **(b) 設定ビューが 2 つ並ぶ** … 状態の同期の問題

★**(b) は「開くときの判定」だけでは塞げない**★ `GoBack` は `OpenSettingsTab` を
通らないからだ。判定がどれだけ正確でも、設定タブを遷移 → 別で設定を開く → 元のタブで
戻る、で 2 枚になる。**判定の改良では届かない領域があった。**

そこで (a) を A-2 で、(b) を B-1 で別々に塞ぐ二段構えにした。

### 修正 A-2 — 判定を「ページ自身に聞く」方式へ

```vba
Private Function IsSettingsView(ByVal pane As Wv2Pane) As Boolean
    js = "(function(){try{return {s:(window.__wv2Settings===true)?'yes':'no'};}" & _
         "catch(e){return {s:'no'};}})()"
    res = pane.EvalSync(js, 2)
    If Not pane.LastEvalOk Then Exit Function    ' 判定できない = 設定画面ではない
    IsSettingsView = (InStr(1, res, """s"":""yes""") > 0)
End Function
```

- **アドレスの表現にも遷移経路にも依存しない。** 戻るで復帰したタブも正しく拾える
- ★**判定の権威を、状態を実際に持っている側に置く** (設計原則91)★ フラグは嘘をつくが、
  ページ自身は嘘をつけない
- **判定できないときは False (安全側)。** 読み込み中・Close 済み・in-callback はすべて
  「設定画面ではない」と扱う。取りこぼしても新しい設定タブが開くだけで、
  誤って別ページのタブを掴むより害が小さい (設計原則93 の `LastEvalOk` で区別)

## K-5 段階 ― ★WebView2 を起動すると VBE の IME 入力でクラッシュする★

### 発端

たーぼーさんの報告 (2026-08-24):

> 「実行用」を実行した後、イミディエイトウィンドウで日本語入力オンの状態で
> 1 文字でもタイプしたら Excel がクラッシュする。日本語入力オフなら入力できるし、
> 日本語をコピペして実行する場合は問題ない。

★再現性があり、しかもクラッシュ (作業内容が飛ぶ)★ ので優先して調べた。

### 切り分け (`CrashTest1`～`12` を `Module1` に常設)

| 条件 | 症状 |
|---|---|
| `Wv2Log` だけ (`LogStart` / `LogI` / `LogStop` / `LogFlush` / `LogEcho`) | ★一度も落ちない★ |
| ファイルを開いたまま `Show` / `Dir` で列挙してから `Show` | ★落ちない★ |

| `Spa` + タブ追加 | 不安定。★フォームを閉じた後は確実に落ちる★ |

★**「WebView2 を一度でも起動したか」だけが確実な境界**★。
そして ★**フォームを閉じて WebView2 を解放しても回復しない**★。

### 見立て

★IME の入力コンテキスト (HIMC) はスレッド単位で管理される★。WebView2 は
Chromium 由来の自前の IME 処理を持ち、そのウィンドウは **Excel と同じ UI スレッド**に
`hWnd_Frame` の子として作られる。つまり ★VBE のイミディエイトウィンドウと
WebView2 が同じスレッドの IME を奪い合っている★。

`Full` の方が早く症状が出るのは、`NavBar` のアドレスバーという
★`input` を持つ WebView2★ が最初から居るためと考えられる。
「コードウィンドウにフォーカスを移すと回避できることがある」という観察は、
★フォーカス移動で IME コンテキストが張り直される★ことの傍証。
ただし ★条件は揺れる (レース)★ ので、回避としては当てにできない。

★仕様事実20 (WebView2 のイベント中にブレークするとクラッシュ) と同じ族★ ――
**WebView2 と VBE が同一プロセス・同一スレッドに同居していることの副作用**で、
**我々のコードには直す場所が無い**。

### ★対処: 打つ必要をなくす★

回避の本命は ★イミディエイトに日本語を直接打たないこと★。そこで
**打つ必要をなくす**方向に手を打った:

- `Module1` の日本語 Sub 名 (`実行用` / `実行用2` / `実行用3`) に
  ★英数字の別名 `Boot` / `BootNoQuiet` / `BootMaps`★ を足した
- 検証 Sub は元々英数字 (`Test_D7_Sheet` 等) なのでそのままで安全
- どうしても日本語が要るときは ★コピペ★ (これは安全と確認済み)
