## 事前調査でわかったこと

### 1. SeleniumVBA の待機 API (開発メモの申し送りで「調べる価値がある」とした件)

公開ドキュメントを確認した。

| API | 役割 |
|---|---|
| `driver.ImplicitMaxWait = 10000` | ★主役★ 以後の **FindElement 呼び出しすべて**に暗黙のリトライを掛ける |
| `driver.Wait 1000` | ただのスリープ |
| `SetScriptTimeout` / `SetPageLoadTimeout` | スクリプト実行 / ページ遷移のタイムアウト |
| `WaitForDownload` | ダウンロード完了待ち |

★**`WaitUntil(条件)` 形の明示 API は文書化されていない。**★
つまり SeleniumVBA の答えは「**要素探しに暗黙のリトライを畳み込む**」であって、
汎用の待機述語を提供する形ではない。

**評価**: 「一番よく要る待ち = 要素が現れるまで」を、新しい API を増やさずに解いている。
学ぶべき点は多いが、**そのまま真似すると D-2 で決めた規約と衝突する** (論点2 参照)。

### 2. 書き込み系 JS の制御フロー (JScript で 14/14 検証済み)

★**`el.value = x` だけでは React / Vue は気づかない**★ これが SPA 対応の核心。
フレームワークは値の変更を「ネイティブ setter + input イベント」で検出するため。

検証した制御フロー:

```js
var d = Object.getOwnPropertyDescriptor(e.constructor.prototype, 'value');
if (d && d.set) { d.set.call(e, v); } else { e.value = v; }
e.dispatchEvent(new Event('input',  { bubbles: true }));
e.dispatchEvent(new Event('change', { bubbles: true }));
```

確認した項目: descriptor があればそれを使う / 無ければ直接代入 / 例外時も値は入る /
どの経路でも `input` → `change` の順で発火する / `click()` の有無による分岐 /
`setAttribute`。

### 3. D-2 の資産 (そのまま使える)

- `EvalSync` (D-1) … 同期評価。in-callback ガードつき
- `JsRegistryPrologue()` … 自己生成プロローグ (設計原則92)。注入しない
- `Elem_Read` … 世代チェック + 高速パス + `{s:..., g:...}` を返す型
- `JsQuote` … VBA ソースにエスケープ列を出さずに JS 文字列を作る
- `LastOk` / `LastError` … 失敗と「値が無い」の区別 (設計原則93)

**書き込み系は `Elem_Read` をそのままなぞれば作れる。** 新機構は要らない。

## ★実装前に実測すべき未知 (最優先)★

### 未知1: `ExecuteScript` は Promise を待つか

**これが論点3 の前提を決める。**

- **待たないなら**: JS 側で `await` する待機は書けない。VBA 側でポーリングするしかない
- **待つなら**: JS 側で完結でき、往復が 1 回で済む。設計が大きく変わる

私の見立ては「**待たない** (Promise オブジェクトが `{}` としてシリアライズされる)」だが、
★推測なので必ず実測する★。確かめる Sub の案:

```vba
Public Sub Test_D3_Probe_Promise()
    Dim p As Wv2Pane
    Set p = UserForm1.GetActivePane
    Wv2Log.LogI "同期の値      : " & p.EvalSync("1+1")
    Wv2Log.LogI "Promise       : " & p.EvalSync("Promise.resolve(42)")
    Wv2Log.LogI "遅延 Promise  : " & _
        p.EvalSync("new Promise(function(r){setTimeout(function(){r(7);},300);})")
    Wv2Log.LogI "LastEvalOk    : " & p.LastEvalOk & " / " & p.LastEvalError
End Sub
```

`42` や `7` が返れば待つ。`{}` や `undefined` なら待たない。

### 未知2: 待ちループ中のネスト

`WaitFor` は `EvalSync` を何十回も撃つ。`EvalSync` は内部で `DoEvents` を回すので、
★**待ちループ全体が長い DoEvents 区間になる**★。

- 仕様事実20 (EBMode) の危険域が**秒単位に伸びる**。`WaitFor` 中は絶対にブレークできない
- `m_evalDepth` のネスト検出ログが毎回出ないか (ログが埋まる)

### 未知3: フレームワークに本当に伝わるか

自前の素の HTML では `el.value = x` でも動いてしまうので、**検証にならない**。
プローブ HTML に「React 風の監視」を仕込む必要がある
(`Object.defineProperty` でネイティブ setter を横取りし、setter 経由の代入だけを数える)。

## 論点 (10 件)

### 論点1: この回のスコープ ★最初に決める★

| 案 | 内容 |
|---|---|
| **A (推奨)** | **書き込み・操作 + DOM 条件待ち** (`WaitFor` / `WaitGone`) |
| B | 書き込み・操作だけ。待ちは D-4 |
| C | A + 静穏待ち (MutationObserver / network idle) まで |

**A 推奨。** B は「`.Click` を入れた瞬間に待ちが要る」問題をそのまま残す
(開発メモの申し送りで既に指摘済み)。C は 1 回に詰め込みすぎで、
静穏待ちは設計原則92 との整合や `fetch` ラップの是非など別に論点が要る。

### 論点2: 待ちの形 ★本丸★

| 案 | 内容 |
|---|---|
| A | 明示待ちだけ。`Wv2Pane.WaitFor(selector, timeoutSec)` → `Wv2Element` |
| B | 暗黙待ちだけ。`QuerySelector` が内部でリトライ (SeleniumVBA と同型) |
| **C (推奨)** | **明示待ちを第一級にし、暗黙待ちは opt-in** |

**C 推奨。** 具体的には:

```vba
Set el = p.WaitFor("#result", 5)      ' 現れるまで最大 5 秒待つ
If p.WaitGone(".spinner", 10) Then    ' 消えるまで最大 10 秒待つ
p.ImplicitWaitSec = 5                 ' 既定 0 (無効)。Selenium 流にしたい人向け
```

理由:

- **明示待ちは「何を待つか」がコードに残る。** 読みやすく、失敗したとき何を待って
  いたかが分かる
- ★**暗黙待ちを既定にすると「本当に無い」の確認が毎回タイムアウト待ちになる**★
  D-2 で `Nothing` + `LastEvalOk = True` を「本当に存在しない」と定義した
  (設計原則93)。暗黙待ちが既定だと、この意味が濁るうえに遅くなる
- それでも Selenium 経験者には暗黙待ちが自然なので、**既定オフの opt-in** にして
  両方の流儀を許す

### 論点3: 待ちループをどこで回すか

未知1 の結果しだいだが、**「待たない」が確定した場合**:

```vba
' Wv2Pane.WaitFor の骨格
t = Timer
Do
    Set el = QuerySelector(sel)          ' EvalSync 1 往復
    If Not el Is Nothing Then Exit Do
    If (Timer - t) > timeoutSec Then Exit Do
    DoEvents
Loop
```

★**この間はブレーク厳禁**★ (仕様事実20)。`Test_D3_Wait` のヘルプにも書く。

**対案**: JS 側に「見つかるまでのポーリング」を置き、結果を `postMessage` で返す
(完了待ちを WebMessage 経由にする)。→ **推奨しない。** 保留テーブルが増え、
D-1 で作った `EvalSync` の型から外れる。まずは素直な VBA ポーリングで良い。

### 論点4: ポーリング間隔

| 案 | 内容 |
|---|---|
| **A (推奨)** | 固定 100ms |
| B | 指数バックオフ (50 → 100 → 200ms) |
| C | 間隔なし (`DoEvents` を回すだけ) |

**A 推奨。** `EvalSync` 1 往復が数 ms なので 100ms 間隔なら負荷は無視できる。
C は CPU を焼くうえに、WebView2 側の処理を圧迫する。

### 論点5: 待つ条件に「見えていること」を含めるか

Selenium は `presenceOfElement` と `visibilityOf` を分けている。

| 案 | 内容 |
|---|---|
| **A (推奨)** | **`WaitFor` は存在だけを見る** |
| B | 既定で可視まで待つ (`offsetParent !== null`) |

**A 推奨。** SPA では「DOM にあるが `display:none`」が普通にある。
可視性が要るなら**別 API (`WaitVisible`) にした方が意図が読める**。まず単純な方を出す。

### 論点6: `.Value =` をどうフレームワークに伝えるか ★SPA の核心★

**検証済みの制御フロー** (事前調査 2 参照) を採用する。

論点は「**`input` と `change` の両方を撃つか**」。

- **推奨: 両方。** React は `input`、jQuery 系は `change` を見ることが多い
- 副作用: 素の HTML フォームでも `change` が余分に飛ぶ。実害は小さいと判断
- 対案: `input` だけ → jQuery 系のページで反応しない事故が起きうる

### 論点7: `.Click` の形

| 案 | 内容 |
|---|---|
| **A (推奨)** | `e.click()` があれば使い、無ければ `MouseEvent('click')` を dispatch |
| B | 常に `mousedown` / `mouseup` / `click` を順に dispatch |

**A 推奨。** `e.click()` は正規のクリックイベントを bubbling で発火するので大半は足りる。
B が要るのはドラッグ系 UI で、そこは実需が出てからで良い。

### 論点8: 戻り値の規約

D-2 の `LastOk` / `LastError` (設計原則93) を踏襲する。

| メンバ | 形 | 成否の確認 |
|---|---|---|
| `.Value = v` | Property Let | ★戻り値を返せない★ → `el.LastOk` を見る |
| `.Click()` | Function → Boolean | 戻り値 + `LastOk` |
| `.SetAttribute(n, v)` | Function → Boolean | 戻り値 + `LastOk` |

`Value` だけ戻り値が無いのは VBA の制約。**`LastOk` を見る運用をヘルプに明記する。**

**対案**: `.SetValue(v) As Boolean` を別に用意する → **推奨しない。**
`el.Value = "..."` と書けることが D 軸の使いやすさの核 (コンセプト①)。

### 論点9: 段階の分割

- **D-3** = 書き込み・操作 + DOM 条件待ち
- **D-4** = 静穏待ち (MutationObserver + fetch/XHR カウンタ) と `QuerySelectorAll` / 寿命管理

| `Test_D3_Framework` | ★ネイティブ setter 経由か★ を React 風の監視で確かめる |
| `Test_D3_Wait` | 遅延して現れる要素で `WaitFor` / `WaitGone` |
| `Test_D3_Help` | 手順 |
