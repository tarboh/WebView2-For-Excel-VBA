## D-1 段階 — ExecuteScript の同期取得プリミティブ (EvalSync)

### 位置づけ

ロードマップ R-4 (MSHTML 相当) の第一歩。**要素レジストリや Wv2Element はまだ作らず、
「非同期 API を同期の顔で使う経路が現行アーキテクチャの上で安全に成立するか」だけを
確かめる**ことに絞った段階。ここが通れば以降は案 C-1 の横展開に落ちる。

### 事前調査で分かったこと (思ったより軽かった)

- `View_ExecuteScript` は呼び出しごとに callback ID を採番し独立スロットを取る
  (第9.8c 案 a) = **並行呼び出しが既に安全**
- `View_ExecuteScriptSafe` が `{ok:true,value:…}` / `{ok:false,errorName:…}` を返す (第9.9c)
- `WaitPaneReady` の DoEvents ループが待ちの前例 (`READY_TIMEOUT = 10#`)
- 旧版 (`旧WebView2.cls`、通常サンク方式) に `ExecuteScriptSync` の前例があり、
  フラグ + DoEvents + タイムアウトという骨格は既に通っていた

→ D-1 は「非同期の仕組みを作る」ではなく **「callbackId と結果を突き合わせて待つ層を
1 枚被せる」** 作業だった。

### 論点と決定 (8 件を一括合意)

| # | 論点 | 決定 |
|---|---|---|
| 1 | メソッド名 | 接頭辞なしの `EvalSync`。`View_` / `Ctrl_` は COM のメソッドと 1 対 1 の意味なので、待ちループ内蔵の高レベル API には付けない |
| 2 | 結果の受け口 | callbackId をキーにした保留テーブル (設計原則87)。`UserForm1.OnExecuteScriptResult` 直呼びは Debug.Print だけなので残す |
| 3 | 戻り値の形 | `String` (= value の JSON 表現)。成否は `LastEvalOk` / `LastEvalError`。型変換は D-2 以降 |
| 4 | Safe 経由 | 常に `View_ExecuteScriptSafe` を通す。生だと JS 例外が S_OK + "null" で返り正常な null と区別できない |
| 5 | タイムアウト | 既定 5 秒。超過したら**破棄済みで残し**、遅延到着はそれを見て捨てる |
| 6 | 並行・ネスト | 許容。callbackId で分離されるので取り違えない。深さをログに出すだけ |
| 7 | in-callback ガード | ★本段階の目玉★ `m_inCallback > 0` なら JS を撃たずに即失敗 (設計原則88) |
| 8 | 検証 | `Test_D1_Eval` / `Test_D1_Guard` / `Test_D1_Help` |

### 追加した Public メンバ (Wv2Pane)

- `EvalSync(jsExpr, [timeoutSec=5]) As String`
- `LastEvalOk As Boolean` / `LastEvalError As String`
- `ResetCallbackGuard()` / `InCallbackDepth As Long`
- `Debug_SetInCallback(n)` (検証専用の注入口)

使用例:

```
?UserForm1.GetActivePane.EvalSync("document.title")                        → "Bぷよ"  (引用符付き)
?UserForm1.GetActivePane.EvalSync("document.querySelectorAll('a').length")  → 22
```

### 実装上の事後報告 (設計原則79)

1. **ハンドラを `_Core` に分離した。** 合意時は「各 View_On* の入口で +1、出口で -1」と
   説明したが、実コードは `View_OnNewWindowRequested` に途中 Exit Sub が 5 箇所、
   他も 1 箇所ずつあった。本体を `Private View_OnXxx_Core` にリネームし、同名の Public
   薄いラッパーが `+1 → Core → -1` を行う形にした (7 個)。→ 設計原則89 として一般化。
2. **エラー時もカウンタを戻すが握り潰さない。** `On Error GoTo GuardExit` で戻したあと
   `Err.Raise` で同じエラーを投げ直す。`ComCallbackHandler` にエラー処理は無く従来は
   そのまま伝播していたので、挙動を変えないため。
3. **`OnExecuteScriptCompleted` にはガードを付けていない。** 結果の受け口であり中で
   ユーザーコードが走らないため。付けると EvalSync の DoEvents 中にカウンタが立ち紛らわしい。
4. **JSON の取り出しは Wv2Pane 内の Private 関数 `JsonPickStr` にした。**
   `Wv2Json.JsonGetStr` は設計原則64 により**エスケープを解かない**実装で、二重 JSON
   エンコードされた値の中の最初のエスケープ引用符で切れてしまう。他所から要るように
   なったら Wv2Json へ昇格させる。
5. **`JSON.stringify` で包む形にした。**
   `View_ExecuteScriptSafe("JSON.stringify(" & jsExpr & ")")` を撃つと、Safe が返す
   value が**常に文字列**になり、限定パーサ 1 本で型を問わず取り出せる。

  例外系の `"ok":false` 検出と errorName / errorMessage の取り出しも確認。
  ※ 最初シミュレータが全 NG になったが、原因は `json.dumps` が `": "` と空白を入れる
    ことで、JS の `JSON.stringify` は空白を入れない。**検査側の作り込み不足だった**。
- **予約語チェック (設計原則90)**: 49 個の識別子を照合。`eNum` の事故を受けて常設化。

- **ガード**: `Test_D1_Guard` の 2) で `View_ExecuteScriptSafe` のログが**一切出ない** =

### 確立した設計原則 (86〜90)

- **設計原則86 (D-1) 段階番号は「軸の記号 + 連番」で振る。**
  一本の連番を伸ばし続けると、性質の違う仕事が同じ列に並んで後から読めなくなる。
  軸が変わったら番号を大きくするのではなく記号を分ける。過去の軸は凍結して書き換えない。

- **設計原則87 (D-1) 非同期 API を同期の顔で使うときは、結果を「単一変数」で受けない。**
  callbackId をキーにした保留テーブルで受ける。単一変数だと並行呼び出しで結果を
  取り違える。既に呼び出し側が並行安全に作られているのに (View_ExecuteScript は
  9.8c で callbackId 採番済み)、上位層でその性質を捨てるのは設計の後退である。
  ★タイムアウトしたエントリは削除せず「破棄済み」で残す★ こと。消すと遅れて来た
  完了通知が「知らない ID」になってログが濁り、実際に来たのかどうかも分からない。

- **設計原則88 (D-1) デバッガが使えない領域では「固まる」を「即座のエラー」に変える。**
  仕様事実 14 (イベントハンドラ内から同期待ちするとデッドロック) は、仕様事実 20 に
  よりブレークもステップも打てない領域で起きるので、踏むと原因究明が極端に苦しい。
  踏めないようにガードを置き、拒否理由をログに書き、復帰手段 (ResetCallbackGuard) も
  同時に用意する。ガードの存在自体がドキュメントになる。

- **設計原則89 (D-1) 途中に Exit のある既存プロシージャへ前後処理を足すときは、
  本体を `_Core` に分離して薄いラッパーで包む。**
  入口と出口に 2 行足す方式は、途中 Exit があると戻し漏れの経路を作る
  (View_OnNewWindowRequested は Exit Sub が 5 箇所あった)。ラッパーなら
  `On Error GoTo` で全経路を一点に集約でき、公開名も変わらないので呼び出し側は無改修。
  ★エラーは握り潰さず Err.Raise で投げ直す★ こと (従来の伝播挙動を変えない)。

- **設計原則90 (D-1) 新規識別子は VBA 予約語リストと「大小無視」で照合する。**
  VBA は識別子の大小を区別しないので、`eNum` は予約語 `Enum` そのものになり
  コンパイルエラーになる (D-1 で実際に踏んだ)。見た目が違っても衝突する。
  Python の検査工程に「`Dim x As` / `ByVal x As` / `Private x As` を正規表現で拾い、
  約 170 語の予約語集合と小文字化して突き合わせる」を常設した。

### 確立した仕様事実 (29〜32)

- **仕様事実29 (D-1) ExecuteScript の結果 JSON はキーがアルファベット順に並び替えられる。**
  View_ExecuteScriptSafe の JS は `{ok, errorName, errorMessage, stack}` の順で
  オブジェクトを作っているのに、VBA に届く時点では
  `{"errorMessage":...,"errorName":...,"ok":false,"stack":...}` になっている。
  ランタイムが結果を作り直しているということ。**位置に依存する解析を書くと壊れる。**
  キー名で探すこと。

- **仕様事実30 (D-1) 結果 JSON では `<` が `\u003C` にエスケープされて届く。**
  例外の stack に `at \u003Canonymous>:1:31` として実際に現れた。
  したがって JSON を自前で解くなら **`\uXXXX` の復号は保険ではなく必須**。
  D-2 で innerHTML を取ると全タグがこの形で来る。

- **仕様事実31 (D-1) JSON.stringify(undefined) は undefined を返すため、
  結果オブジェクトから value キーごと消える。**
  `{"ok":true}` だけが届く。これは「戻り値が undefined だった」の合図として使える
  (エラーではない)。EvalSync はこれを検出して文字列 undefined を返している。

- **仕様事実32 (D-1) JS がスレッドをブロックしている間、ExecuteScript の完了通知は
  届かず、ブロックが解けた瞬間にまとめて届く。**
  3 秒のビジーループを 1 秒でタイムアウトさせた検証で、打ち切り後に完了通知が
  遅れて到着した (cb19)。仕様事実 27 (hostObjects.sync 中は呼び出し元ペインの JS が
  完全にブロックされる) と同じ構造で、**待つ側は必ずタイムアウトと遅延到着の始末を
  持たなければならない。**
  ※ JS の構文エラーが errorCode=0 + resultJson="null" で返る件は第9.9c で確認済み。
    D-1 でも同じ挙動を再確認した (EvalSync は syntax-error-or-null として扱う)。

### D-2 以降への申し送り

- 文字列は**引用符付きで返る**。D-2 で `Wv2Element` のプロパティごとに型を決めて剥がす。
- `jsExpr` は「文」ではなく「式」。複数文は即時関数で包む (Safe ラッパーの制約を継承)。
- 要素レジストリ (`__wv2els[]`) は**ページ遷移で消える**ので、`Wv2Element` は
  「Pane 参照 + ハンドル + 世代番号」の 3 つを持たせて古い参照を検出できるようにする。
- `QuerySelectorAll` は JS 側で全ヒットを一括登録しハンドル配列を返せば**往復 1 回**で済む。
  戻り値は VBA 標準の `Collection`。`Wv2Elements` クラスは作らない。
- `Wv2Document` は作らない (Wv2Pane が既に title / URL / readyState / DOMContentLoaded を
  持っており、挟むと二重化するだけ)。検索の入口は `Wv2Pane` に直付け。
- ★`EvalSync` の DoEvents ループ中もブレーク/ステップ実行しないこと★ (仕様事実20 の追補)。
- ★ハンドラ内で JS の結果が要るときは SafeTimer で一拍置いてから呼ぶ★
  (`RequestNewTabAsync` と同じ型)。直呼びは in-callback ガードで即失敗する。

## D-2 段階 — 要素レジストリと Wv2Element の読み取り

### 位置づけ

D-1 で「非同期 API を同期の顔で使う」経路が実証されたので、その上に載る本番の層。
**要素を掴んで値を読む**ところまでを担当し、書き込み (`.Value =` / `.Click`) は D-3、
コレクション (`QuerySelectorAll`) と寿命管理は D-4 に送る。

### 論点と決定 (9 件を一括合意)

| # | 論点 | 決定 |
|---|---|---|
| 1 | JS 側レジストリの注入タイミング | **案c: 注入しない。** 検索式そのものが「無ければ自分で作る」形にする |
| 2 | 世代番号の発行元 | **案b: JS が発行** (`'g' + Date.now() + '-' + Math.random()`)。判定の権威は常に JS 側 |
| 3 | ハンドルの解放 | **案a: 解放しない。** `ClearElementRegistry` を手動掃除用に 1 本だけ |
| 4 | 見つからないときの返し方 | **案a: `Nothing`。** 成否は `LastEvalOk` で区別する |
| 5 | `Wv2Element` の公開メンバ | 読み取り 8 種 (下記)。書き込みは D-3 |
| 6 | 引用符剥がしの置き場所 | **案b: `Wv2Json.bas` に集約** |
| 7 | `QuerySelectorAll` を含めるか | **案a: 含めない (単数のみ)。** JS 側だけ複数対応の形にしておく |
| 8 | 検証ページ | **案b: 自前 HTML を `NavigateToString`** |
| 9 | 検証 Sub | `Test_D2_Find` / `Test_D2_Stale` / `Test_D2_Help` の 3 本 |

### ★論点1: 注入しない (self-bootstrapping)★

`AddScriptToExecuteOnDocumentCreated` (完了ハンドラ用の HandlerKind と vtable が新たに要る)
も、`DOMContentLoaded` での毎回注入 (ハンドラ内なので `EvalSync` が使えず、タブバー /
ナビバー / 設定タブの Pane にも撃たれる) も採らない。代わりに **D-2 の全 JS 式の先頭に
共通のプロローグを置く**。

```js
if(typeof window.__wv2==='undefined'||!window.__wv2){
  window.__wv2={gen:'g'+Date.now()+'-'+Math.random(),els:[]};}
var R=window.__wv2;
```

- 新しい COM 機構が要らない
- 往復が増えない (判定・生成・検索が 1 つの式に入る)
- ページ遷移 / SPA の書き換え / `about:blank` のどれで消えても、次のアクセスで
  自動的に作り直される (設計原則74 と同じ自己修復性)

**欠点**: ページ読み込み**前**にフックを仕込む用途には使えない。それが要るときは
`AddScriptToExecuteOnDocumentCreated` を独立段階で実装する。

### ★論点2: 世代は JS が発行する★

VBA 側でナビゲーションを数える案は、SPA の `pushState` では DOM が残るのにイベントは飛び、
逆にページ内 JS が要素を差し替えてもイベントは飛ばないので**実態とズレる**。
JS 側が発行すれば「レジストリが消える = 世代も消える = 作り直しで必ず別値」が保証される。

`Wv2Pane.m_domGen` は「JS から最後に聞いた世代」のキャッシュで、**高速パスにしか使わない**。
手元の世代とキャッシュが違えば往復せずに stale と確定でき、一致していても JS が作り直して
いるかもしれないので必ず問い合わせる。**キャッシュが古いときは必ず「問い合わせる」側に
倒れる**ので誤判定は起きない。

### ★Nothing と空文字の読み方 (論点4 の規約)★

| 場面 | 判定 |

### 実装上の事後報告 (設計原則79)

- **(a) `JsonPickStr` を `Wv2Pane` から `Wv2Json` へ移設した (Private → Public)。**
  論点6 の合意は「`JsonUnescape` を新設し `JsonPickStr` もそれを呼ぶ形に書き換える」
  だったが、`Wv2Element` も同じ復号を要るため、`Wv2Pane` に Private で残すと 2 実装になる。
  走査部は `Wv2Json.JsonUnescapeAt` に同一移植し、ロジックは 1 文字も変えていない。
  既存の `JsonGetStr` (エスケープを解かない、設計原則64) は**一切変更していない**。
- **(b) `Wv2Element` に `LastOk` / `LastError` を足した (論点5 の 8 メンバ + 2)。**
  読み取り系は失敗時も空文字を返すため、「本当に空」と「stale」を区別する手段が要る。
  `Pane.LastEvalOk` は JS 実行自体の成否なので、stale のとき True になり代用できない。
- **(c) `Elem_Read` / `Elem_CheckStale` の戻り値を Enum でなく `Boolean` + 状態文字列にした。**
  クラスモジュールの `Public Enum` が他モジュールから無修飾で見えるかは本プロジェクトに
  前例がなく (`ControllerState` も `BrowserState` も定義元でしか使われていない)、
  コンパイルエラーになると 1 往復無駄になる。D-1 の流儀にも揃う。

- **Python 先行検証 (34 ケース、NG 0)** — `JsonUnescape` を Python で再現し、

## 外部からの提言 — SPA における「完了待ち」の判定方式 (2026-08-20 受領)

★段階ではない。D-3 / D-4 を設計するときの入力として記録する。★

### 出典

**SeleniumVBA プロジェクトの参画者**から本プロジェクトに寄せられた提言。
たーぼーさん経由で受領。原文:

> SPA対応について少し気になったのですが、HistoryChanged や DOMContentLoaded などを
> 捕捉する仕組みはすでに実装されていますよね。
>
> 一方で、ボタンクリック後に fetch/XHR → React/Vue等によるDOM更新、というように
> 複数の非同期処理が連鎖するケースでは、これから作られる自動操作ラッパー側で
> 「次の操作へ進んでよい」と判断する完了待ちは、どのような方式を採用するのか
> 気になります。
>
> DOM条件待ち、MutationObserver、Network Idle、WebView2の各種イベントなど
> 色々なシグナルが使えそうですが、SPAの場合はどれか一つを見れば確実、
> という決定打がないので悩みどころですね。

### なぜ効くのか

**コンセプト①「Web ページを自動制御することに優れた使いやすさ」の核心を突いている。**

D-2 までで揃ったのは「**今の DOM を読む**」手段 (`EvalSync` / 要素レジストリ /
世代判定) であって、「**変化し終わるのを待つ**」手段はまだ何も無い。
D-3 (`.Click` / `.Value =`) を入れた瞬間に、**操作 → 待ち → 次の操作**という
連鎖が必ず必要になる。そこで待ち方を誤ると、
「ローカルでは通るのに本番で落ちる」自動化になる。

現状の持ち物と、それぞれの届く範囲:

| 持ち物 | 実装済み | SPA の連鎖に届くか |
|---|---|---|
| `NavigationCompleted` | 第9.4b | **届かない** (SPA の画面遷移では発火しない) |
| `DOMContentLoaded` | 第9.9 | **届かない** (初回ドキュメントのみ) |
| `HistoryChanged` | 第9.9 / 9.10 | **部分的** (pushState を伴う遷移は拾えるが、伴わない再描画は拾えない) |
| `EvalSync` | D-1 | 任意の JS を同期評価できるので、**待ちの土台にはなる** |
| 要素レジストリ + 世代 | D-2 | 「DOM が作り直されたか」は分かるが、「落ち着いたか」は分からない |

### 提言が挙げているシグナルと、現時点での見立て

**まだ決めない。** D-3 / D-4 の論点として一括合意にかけるための材料として置く。

| シグナル | 長所 | 弱点 |
|---|---|---|
| **DOM 条件待ち** (指定のセレクタが現れる/消える/テキストが変わるまで) | **意図が明示的**。誤検知が少ない。実装が軽い (`EvalSync` のループで足りる) | 呼び出し側が「何を待つか」を毎回書く必要がある。使いやすさの負担 |
| **MutationObserver** | DOM の変化そのものを捉える。汎用 | 「変化が止まった」の判定に**静穏時間 (quiet period)** の概念が要る。アニメーションや広告で永久に静まらないページがある |
| **Network Idle** | フレームワーク非依存。fetch/XHR の連鎖に強い | WebView2 から直接は取れない。`fetch` / `XMLHttpRequest` を JS 側でラップして数える必要がある (**設計原則92 の自己生成プロローグと相性が良い**)。ロングポーリングや WebSocket で永久に idle にならないページがある |
| **WebView2 の各種イベント** | 既に配線済み | 上表のとおり SPA の連鎖には届かない |

**現時点の私見 (未合意)**: 決定打が無いという指摘はそのとおりで、
**単一のシグナルを選ぶのではなく「合成 + 明示的な打ち切り」に寄せる**のが筋に見える。

- 既定は「**DOM 条件待ち**」— 使う側が待ちたいものを書ける形を第一級にする。
  コンセプト①は「万能な自動判定」ではなく「**書きやすさ**」なので、
  `WaitFor("#result", 5000)` のような形が本命になりうる。
- 補助として「**静穏待ち**」(MutationObserver + Network カウンタの合成) を用意し、
  待つ対象が特定できないときの保険にする。
- **必ずタイムアウトを持たせ、超えたら失敗として返す** (設計原則93 の
  `LastOk` / `LastError` の型に載せる)。★仕様事実20 / 14 があるので、
  待ちループは必ず `EvalSync` と同じ in-callback ガードの下に置くこと。★
