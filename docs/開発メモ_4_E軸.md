### ★発見: VBA のソースはプロジェクトのコードページで保持される★

エクスポート結果を配布物と全数照合したところ、**`⚙` `⟳` `⇄` `↔` `〜` `—` が
すべて `?` に化けていた。**

**切り分け**: エクスポートが落としたのか、ブックが既に失っているのかを判定するため、
`Export` ではなく **`CodeModule.Lines` を COM 経由 (BSTR = UTF-16) で読み出して**
UTF-8 で保存し、比較した。結果、**COM 経由で読んでも `?` のまま**だった。
すなわち**ブック側で既に失われている**。エクスポートの問題ではない。

一方 `★` は 1,517 個、`←` `→` `①②④` も無傷で残っていた。これらは CP932 にある文字。

**実測 (`src/` の `.bas` + `.cls` 全 17 本)**:

| 項目 | 数 |
|---|---|
| `?` の総数 | 238 個 |
| ★うち化けて `?` になったもの★ | **76 個** |
| 正当な `?` (URL のクエリ文字列 / JS の三項演算子 / イミディエイトの `?` 短縮形 / 疑問文) | 162 個 |

化けた 76 個の内訳:

| 文字 | コード | 個数 | 代替候補 |
|---|---|---|---|
| `〜` | U+301C WAVE DASH | 33 | `～` U+FF5E |
| `⚙` | U+2699 | 28 | `[設定]` |
| `⇄` | U+21C4 | 6 | `⇔` |
| `↔` | U+2194 | 5 | `⇔` |
| `⟳` | U+27F3 | 3 | `[更新]` |
| `—` | U+2014 EM DASH | 1 | `―` U+2015 |

**被害の範囲**: 全部**コメントと `Debug.Print` の案内文**の中にある。
**実行ロジックと HTML/JS は無傷。** タブバーの歯車ボタンは HTML の実体参照
`&#9881;` で描いているため、**画面の見た目には一切影響していない。**

配布物の該当行はすべて `?` 置換後の形で `src/` に存在することを確認済み
(照合できなかった行はゼロ)。**したがって上の 76 個が被害の全数。**

### 検査器 `tools/check_cp932.py`

```
python tools/check_cp932.py
```

`src/` を走査し、**CP932 で往復できない文字**を行・桁つきで報告して代替候補を出す。
問題があれば終了コード 1。

**★「encode できるか」では不十分★** 失敗モードが 2 つあるため:

| モード | 例 | 結果 |
|---|---|---|
| encode 自体が不可 | `⚙` `⟳` `⇄` `↔` `—` 絵文字全般 | `?` になる (目視で気づける) |
| **encode は通るが別の字に化ける** | `〜`→`～`、`−`(U+2212)→`－`、`¢`→`￠` | **黙って置き換わる** |

さらに **Python の `cp932` コーデックは Windows より寛容**で、`〜` (U+301C) は
Python では encode が通るが **VBA では `?` になる。** 往復判定ならどちらのモードも捕まる。

**検査器自身の検証**: `src/` に対しては問題ゼロ (ブック由来なので当然)。
そこで**既知の壊れる文字を含む配布物** (`Downloads/Wv2TabBar.cls`) に掛け、
歯車 4 個を正しい行・桁で検出し終了コード 1 を返すことを確認した。
★検査器は「発火すること」を確かめて初めて信用できる。★

### 確立した設計原則 (94〜95)

## ★ 設計原則 94 — 変換を挟む往復は「戻したものが元と一致するか」で判定する ★

片道の成否 (encode できたか) では不十分。**best-fit 変換のように「成功したのに
別のものになる」経路がある。** CP932 では `〜`(U+301C) が `～`(U+FF5E) に、
`−`(U+2212) が `－`(U+FF0D) に黙って置き換わる。encode は成功するので
エラーにならず、目視でも気づけない。

往復させて元と一致するかを見れば、encode 不可と best-fit 置換の**両方**が同じ
判定で捕まる。`export.ps1` の変換検証も `check_cp932.py` もこの形にしてある。

※ 実装側の教訓として、**検証に使うライブラリが本番と同じ変換表を使っているとは限らない。**
   Python の `cp932` は Windows の CP932 より寛容で、`〜` を通してしまう。
   往復判定ならライブラリ差にも耐える。

## ★ 設計原則 95 — 開発環境の制約は、その場で直さず検査器にして常設する ★

設計原則90 (予約語チェックの常設化) の一般化。一度踏んだ環境固有の制約は、
**次に踏むのが数か月後**であることが多く、そのときには経緯を忘れている。

直した瞬間に検査器へ落とし、定型の検査セットに組み込む。**そして検査器は
「既知の悪いデータに対して発火すること」を確かめてから信用する。**
`src/` に問題が無いのは当たり前 (ブック由来なので既に失われている) で、
それだけでは検査器が動いている証拠にならない。

### 確立した仕様事実 (35〜38)

## ★ 仕様事実 35 — VBA のソースはプロジェクトのコードページで保持され、表現できない文字は import 時に永久に失われる ★

日本語環境ではコードページ 932。CP932 で表現できない文字は、モジュールを import した
時点で `?` に置き換わり、二度と戻らない。**ファイル側の文字コードとは無関係**で、
UTF-8 で渡そうが同じ結果になる。失敗モードは 2 つ (設計原則94 参照)。

現行ブックには既にこの被害が 76 文字分入っている
(`〜`×33 / `⚙`×28 / `⇄`×6 / `↔`×5 / `⟳`×3 / `—`×1)。
**すべてコメントと `Debug.Print` の案内文の中で、実行ロジックと HTML/JS は無傷。**

## ★ 仕様事実 36 — VBE の Export は CP932 / CRLF / BOM なしで書き出す ★

`VBComponent.Export` が書くファイルはシステムの ANSI コードページ (CP932) で、
改行は CRLF、BOM は付かない。`.frx` はバイナリ。

逆に **Import は BOM なし UTF-8 を受け付ける** — これは第9.x 以降 Claude が出力した
UTF-8 ファイルを取り込み続けて日本語コメントが正しく入っている実績からの推定で、
**E-2 (import.ps1) で直接確認する。**

## ★ 仕様事実 37 — `.frx` はエクスポートのたびに数バイト変化する ★

フォームの中身を一切変えていなくても、`.frx` の内容は毎回変わる
(`TimerForm.frx` で 5 バイト、`UserForm1.frx` で 28 バイト。
5 バイト単位のまとまりで変化しており、OLE のタイムスタンプらしい)。

このためフォームを毎回エクスポートすると差分が汚れる。`export.ps1` の既定では
書き出さない。

## ★ 仕様事実 38 — VBA は識別子の大小を最初の宣言に合わせて統一し、既存の出現箇所も書き換える ★

`Wv2Element` の `Public Property Get Value()` はブック内で `value` になっており、
`Wv2Thunks` の `ByVal Y As Long` は `y`、`ByVal ptr As LongPtr` は `Ptr` になっていた。

**VBA が同名識別子の綴りをプロジェクト全体で統一するため。** 動作は変わらないが、
エクスポートするとソースの見た目が変わるので、**配布物と突き合わせるときに
「差分が出た = 版ズレ」と誤読しないこと。**
