## D-4 で解きたいこと

D-3 で入ったのは「**DOM の条件**を待つ」手段 (`WaitFor` / `WaitGone`)。
外部からの提言が指摘した問題は**まだ半分しか解けていない**:

> ボタンクリック後に fetch/XHR → React/Vue 等による DOM 更新、というように
> 複数の非同期処理が連鎖するケースで、「次の操作へ進んでよい」と判断する完了待ち

**待つ対象が特定できないとき**にどうするか。それが D-4 の本題。

`WebDriver BiDi for SeleniumVBA` (hanamichi77777、MIT、v4.3) の

### 既定値 (そのまま出発点にできる)

| 定数 | 値 | 意味 |
|---|---|---|
| `DEFAULT_IDLE_STABLE_MS` | **500** | 静穏窓。この時間 DOM が動かなければ「静か」 |
| `DEFAULT_IDLE_TIMEOUT_MS` | **10000** | 待ちの上限 |
| `DISCOVERY_DOM_POLL_MS` | **100** | DOM ポーリング間隔 (★D-3 で我々が選んだ 100ms と同じ★) |
| `DEFAULT_IGNORE_NETWORK` | `google-analytics, doubleclick, /collect, /beacon, .woff2, favicon.ico` | 静穏判定から外す要求 |
| `DEFAULT_IGNORE_SELECTORS` | `script, link, input[type='hidden'], .vba-ignore, ...` | 静穏判定から外す DOM 変化 |

### ページ内プローブ `window.__vbaIdleProbe` の構造

★**向こうもページ内に JS を仕込んでいる**★ (BiDi があっても DOM 側は結局これ)。

```
{ version, inflightFetchCount, inflightXhrCount, lastMutationTs,
  changeList, inflightUrlCounts, selectors, ignoreNetwork,
  baseObserver, fetchWrapper, xhrOpenWrapper, xhrSendWrapper, inputSetterWrapper,
  armDomSignal(xpath, attrs), armVisSignal(...), disarmSignal() }
```

- `window.fetch` と `XMLHttpRequest.prototype.open/send` を**ラップして in-flight を数える**
- `MutationObserver` を `document` に張り、`{childList, characterData, subtree, attributes}` を観測。
  ignore セレクタに当たる変化は数えない
- 静穏の判定は **`inflight == 0` かつ `now - lastMutationTs >= stableMs`**

### ★実装から学んだ設計上の急所 4 つ★

1. ★**健康診断 (`probeHealth`) を持っている**★
   `window.fetch === p.fetchWrapper` などで**ラップが今も生きているか**を毎回確かめる。
   フレームワークが後から `fetch` を差し替えることがあるため。
   `SPA_PROBE_VERSION`(=39) の版番号も持ち、食い違えば作り直す。
   → ★これは我々の設計原則92 (自己修復) と設計原則91 (権威は JS 側) そのもの★

2. ★**シグナルが当たったら静穏タイマーを 0 に戻す**★
   「証拠が来た直後の 1 ポーリング分」ではなく、**証拠の後にもう一度まるごと静穏窓を取る**。

3. ★**ナビゲーションで arm が壊れたら、黙って再 arm せずタイムアウトさせる**★
   (`SPA-SIGNAL-LOST`)。**fail-visible**。D-2 の stale の扱いと同じ思想。

4. ★**arm なしで走らせた回は「発見のための回」**★
   静穏だけでは「アプリが完了した」と「アプリが無視した」を区別できない。
   だから**拒否せずに走らせ、ログに残った DOM パスを次回 arm させる**。
   `slackMs = domQuietMs - minStableMs` を出し、**100ms を切ったら「際どい」**と警告する。

### 使う側の書き味 (コンセプト①の参考)

```vba
bidi.AddIdleIgnoreNetworkPattern "www.example.com/cdn-cgi/rum"
bidi.ArmContentSignal "//*[@id='table-body']"
bidi.ExecuteClickByXPath "//a[@id='2015']"     ' ← クリック自体が待つ
```

★**向こうは「操作が待つ」が既定**★。arm は「何を待つか」を絞り込む指定。
D-3 の `.Click` は待たない設計なので、ここは我々の論点になる (論点7)。

## 事前調査 (2) 我々の環境での制約

| | 向こう | こちら |
|---|---|---|
| ネットワーク観測 | BiDi でプロトコルから取れる | ★ページ内で `fetch`/`XHR` をラップするしかない★ |
| DOM 変化 | ページ内プローブ | 同じ (`MutationObserver`) |
| 取り出し | イベント購読 (push) | `EvalSync` のポーリング (pull、1 往復 38ms) |

**pull しかない点は問題にならない。** プローブ側が「最後に動いた時刻」を持っていれば、
VBA は 100ms ごとに「今どうか」を聞くだけでよい (D-3 の待ちループと同じ形)。

★**本当の難所は「いつラップを仕込むか」**★
`fetch` のラップは**要求が始まる前**に入っていないと数え漏らす。しかし設計原則92 で
「注入しない・使う式が自分で用意する」と決めており、プロローグは**遅延生成**である。

→ **arm-then-act がこの緊張を解く** (D-3 の記録に書いたとおり)。
操作の直前に arm する運用なら、arm の時点でラップを作れば必ず操作より前になる。
★「arm 以降に始まった要求のみを数える」と仕様を切ってしまう★のが筋に見える。

## ★実装前に実測すべき未知★

D-3 の教訓 (設計原則103) に従い、**プローブ自体が測れているか**を先に確かめる。

### 未知1: ラップは生き残るか

実サイトで `fetch` / `XHR` のラップが、フレームワークの後続処理で差し替えられないか。
向こうが `probeHealth` を持っている以上、**差し替えは実在する**と考えるべき。
→ 健康診断の要否と、作り直しの頻度を測る。

### 未知2: `MutationObserver` の負荷

重いページ (Google Flights クラス) で `subtree: true, attributes: true` の観測を張ったまま
`EvalSync` を 100ms ごとに撃って、往復が 38ms のままか。
★遅くなるなら観測の粒度 (attributes を外す等) が論点になる★

### 未知3: SPA の pushState 遷移でプローブは生き残るか

D-2 の世代 (`window.__wv2.gen`) はページ遷移で作り直される。**pushState では JS の実行環境は
生き続ける**ので、プローブは残るはず。だが `lastMutationTs` は遷移直後に大量の変化を拾う。
→ 「遷移直後に静穏窓が満たされない」ことを確かめる (それが正しい挙動)。

### 未知4: 我々のプローブと `Wv2TabBar` / `Wv2NavBar` / 設定タブの干渉

D-2 の設計 (注入しない) は「タブバー等の Pane に無駄な注入をしない」ことも理由だった。
プローブは**コンテンツ Pane にしか作られない**ことを確認する。

## 論点 (10 件)

### 論点1: この回のスコープ ★最初に決める★

| 案 | 内容 |
|---|---|
| **A (推奨)** | **静穏待ち一本** (プローブ + 健康診断 + 明示シグナル + 診断ログ) |
| B | A + `QuerySelectorAll` + 要素の寿命管理 |
| C | A + Shadow DOM 貫通 |

**A 推奨。** 静穏待ちだけで「ページ内プローブの新設 + ネットワーク/DOM の観測 +
健康診断 + シグナル + 診断ログ」と、D-2 に匹敵する量がある。
B の 2 つは**独立して実機検証できる**ので D-5 に分けた方が事故が小さい。
C (Shadow DOM) は**検索の話**であって待ちの話ではないので、軸として別に立てる。

### 論点2: プローブの入れ方

| 案 | 内容 |
|---|---|
| **A (推奨)** | **自己生成プロローグの拡張** (設計原則92 を維持)。「arm 以降のみ数える」と仕様を切る |
| B | `AddScriptToExecuteOnDocumentCreated` を新規実装し、読み込み前に仕込む |

**A 推奨。** B は新しい COM 機構 (完了ハンドラの HandlerKind と vtable) が要るうえ、
D-2 で「注入しない」と決めた判断を覆すことになる。
**A の弱点は「arm 前に始まった要求を数えられない」ことだけ**で、arm-then-act の
運用ならそれは仕様として受け入れられる。

★ただし B が要る場面は残る★ ページ読み込みそのものの完了を待ちたい場合。
そこは既存の `NavigationCompleted` / `DOMContentLoaded` で足りるはずなので、
**D-4 では A で通し、足りないと分かった時点で B を独立段階にする。**

### 論点3: 健康診断を入れるか

- **推奨: 入れる。** 版番号 + 各ラップの同一性 (`window.fetch === p.fetchWrapper` 等) を
  毎回確かめ、壊れていれば作り直す。
- 参考プロダクトが実装しているということは**実際に壊れる**ということ。
- 設計原則92 の自己修復性を、D-2 の「無ければ作る」から
  **「壊れていたら作り直す」まで広げる**形になる。

### 論点4: 静穏の判定式と既定値

**推奨: 参考プロダクトと同じところから始める。**

```
静穏 = (inflightFetch + inflightXhr == 0) かつ (now - lastMutationTs >= stableMs)
既定: stableMs = 500 / timeout = 10 秒 / ポーリング = 100ms (D-3 と同じ)
```

- ★`EvalSync` 1 往復が 38ms なので、実効の判定間隔は約 140ms (仕様事実52)★
  500ms の静穏窓に対しては十分細かい。
- `slackMs = 実際の静穏 - stableMs` を返して、**際どさを呼び出し側が見られるようにする**。

### 論点5: ノイズ除外を入れるか

- **推奨: 入れる。** ネットワークは URL パターン、DOM はセレクタで除外する。
  既定リストは参考プロダクトのものを流用 (analytics / beacon / favicon / script / link 等)。
- ★**広すぎる除外は「早すぎる静穏」を生む**★ ことを API のコメントに明記する。
- 遮断 (要求を送らせない) は**やらない**。手段が無いし、ページの挙動を変える。

### 論点6: 明示シグナル (Arm 系) を D-4 に含めるか

- **推奨: 含める。最小 2 種。**

| API | 意味 |
|---|---|
| `ArmContentSignal(selector)` | ★既存の★ 部分木が書き換わるのを待つ。arm 時に無ければ即失敗 |
| `ArmNetworkSignal(pattern)` | URL がパターンに一致する要求の完了を待つ |

- ★**静穏だけでは「完了した」と「無視された」を区別できない**★ (向こうの言葉)。
  重要な操作には明示シグナルが要る。
- **ワンショット**。次の待ちで消費される。同じ操作を 2 回するなら 2 回 arm する。
- **シグナルが当たったら静穏タイマーを 0 に戻す** (証拠の後に改めて静穏窓を取る)。
- ナビゲーションで arm が壊れたら**黙って再 arm せずタイムアウトさせる** (fail-visible)。
- `ArmVisibilitySignal` は D-5 送り (`WaitVisible` と一緒に入れる方が自然)。

### 論点7: 待ちを操作に結合するか ★API の顔★

| 案 | 内容 |
|---|---|
| **C (推奨)** | **独立 API を第一級 + opt-in で自動化** (D-3 の `ImplicitWaitSec` と同じ二段構え) |
| A | 独立 API のみ (`p.WaitSettled 10`) |
| B | `.Click` の既定を「待つ」に変える (参考プロダクトと同じ) |

**C 推奨。** 具体的には:

```vba
p.WaitSettled 10                  ' 明示。第一級
p.AutoWaitAfterAction = True      ' 既定 False。以後 .Click / .Value = の後に自動で待つ
```

- B は**D-3 の契約を壊す**。`.Click` は「JS が例外なく走った」を返す約束で、
  待ちを混ぜると戻り値の意味が濁る (D-3 の最も誤解しやすい点をさらに複雑にする)。
- A だけだと、毎回書くのが面倒で結局使われない (コンセプト① に反する)。
- ★`ImplicitWaitSec` (既定 0) で同じ形を既に採っている★ ので、流儀が一貫する。

### 論点8: 戻り値と命名

- **推奨: `WaitSettled(timeoutSec) As Boolean`**
  `True` = 静穏に達した / `False` + `LastEvalOk=True` = 時間切れ (正常) /
  `False` + `LastEvalOk=False` = 失敗 (in-callback / プローブ不整合)。**D-3 と同じ規約。**
- ★名前で「推測」であることを匂わせる★ `WaitIdle` より `WaitSettled` (落ち着いた) を推す。
  「idle = 何も起きていない」と読めてしまうと、保証と誤解される。
- 診断値 (`slackMs` / 最後の in-flight 数) は `LastInfo` 相当の口で読めるようにする。

### 論点9: 診断ログ (Discovery Log 相当) を含めるか

- **推奨: 最小形で含める。** K-1 の `Wv2Log` に、
  「要求の開始/完了 / DOM 変化のバースト / 除外したノイズ / 静穏判定と slackMs」を
  時系列で吐く。
- ★**これが無いと「何を待つべきか」を決められない**★ 向こうの最大の発見がここ。
  arm なしで 1 回走らせ、ログに出た DOM パスを次回 arm する、という運用が成り立つ。
- 我々の開発サイクル (Claude がログファイルを直接読む) と噛み合う。
- **常時 ON にはしない。** `Wv2Log` の DEBUG レベルか、明示の開始/停止で。

### 実サイトは ★Google Maps★ に決定 (論点10)

**理由: 業務での実用を考えると Maps が動くとありがたい** (たーぼーさん)。

★**静穏待ちにとって Maps は最も過酷な部類**★ タイル取得とアニメーションが止まらないので、
素朴に静穏を待つと**永久に静まらない**。だがそれは採用しない理由にならない:

- ★ノイズ除外 (論点5) と明示シグナル (論点6) が本当に効くのかを試せるのは、こういうページだけ★
  自前 HTML では絶対に出ない
- 業務で実用したいなら、**動かないと分かることにも価値がある** (手に負える範囲の線引き)
- Maps でも業務で使うのは**DOM 側** (検索候補 / サイドパネル / 経路の所要時間)。
  canvas の地図そのものを自動操作したいわけではない

役割を分ける:

| | 対象 | 役割 |
|---|---|---|
| 主 | 自前 HTML | **決定的な合否判定** (回帰にも使う) |
| 副 | **Google Maps** | ★現実確認★ 未知1 (ラップの生存) / 未知2 (負荷) と、除外・シグナルの実効性 |

★**Maps のどの流れを狙うかは未確定**★ (場所検索 / 2 地点の経路と所要時間 / 複数住所のバッチ)。
arm する対象が変わるので、実サイト検証の前に確定させること。
**プローブ本体はこの答えに依存しない**ので、先に着手してよい。
